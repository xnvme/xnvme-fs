# Adapters

Two database engines store their files on a pool: DuckDB through the
extension `xnvme_fs` in `adapters/src`, and RocksDB through the plugin
`xnvme_fs` in `adapters/rocksdb`. Each adapter implements the engine's own
file system interface on the [C API](../api.md), and is an example of how a
program uses xnvme fs:

* The adapter keeps one session per pool and process. It makes the session
  when the pool is first used, and makes a new one when the session's
  connection has failed.
* The adapter opens one file of the pool for each file of the engine.
* Reads and writes are synchronous on the engine's threads.
* Where the engine has several reads or writes to start at once, the adapter
  submits asynchronous requests.

Both adapters use a pool in the same way. Requests on metadata, which open
and create files, lease extents and commit files, go over the socket of
`xnvme fs serve`. Reads and writes of data go from the engine's own threads
to the members, and each thread submits them on queues of its own.

## The C++ layers

Both adapters call the C API through two C++ headers in `adapters/include`.

`yace/xnvme_fs.hpp` is generated by yace from `libxnvme_fs.h` and committed;
`adapters/scripts/generate-cpp.sh` writes it, and with `--check` fails where
the committed header differs from what yace generates. In the namespace
`xnvme_fs`, the header has the classes `session`, `file` and `req`, whose
destructors free the C handle, and the functions `connect()`, `req_new()` and
`errmsg()`. A call that fails throws `xnvme_fs::detail::failure`, a
`std::system_error` whose `code()` is the errno and whose `what()` is the name
of the C function and the message of `xnvme_fs_errmsg()`.

`xnvme_fs.hpp` adds, in the namespace `xnvme::fs`, the classes `Session` and
`File` that both adapters use on top of the generated header. `Session`
records whether its connection to the server has failed. A call that fails
with `ENOTCONN`, `ECONNRESET`, `EPIPE` or `EPROTO` sets the record, and
`Session::Alive()` then returns false. The adapter makes a new session when
`Session::Alive()` returns false:


`Session::List()` reads a directory 256 entries at a time. When
`xnvme_fs_list()` fails with `ESTALE`, the names changed between two requests,
and `Session::List()` starts again from the first entry:

```{literalinclude} ../../adapters/include/xnvme_fs.hpp

:end-before: void Mkdir(const std::string &name) {
:dedent:
:tab-width: 4
```

A `File` is one open of a file, and several threads can use one `File` at
the same time. `File::Id()` returns the same value for every `File` that is
open on one file of the pool. The DuckDB adapter uses `File::Id()` to find the
writes in flight to a file. `File::Handle()` returns the generated `file`,
whose `submit()` starts a request.

## Building

The adapters' build finds `libxnvme-fs` with pkg-config, as the meson project
at the top of the repository installs it beside xNVMe. In `adapters`:

```
GEN=ninja make release      # DuckDB with the extension, behind_test, xnvme-fs-bench
make rocksdb                # db_bench and RocksDB's tests with the plugin, in a Debug build
```

`make rocksdb` links `adapters/rocksdb` into RocksDB's source tree as
`plugin/xnvme_fs` and builds RocksDB with `-DROCKSDB_PLUGINS=xnvme_fs`. The
pages [DuckDB](duckdb.md) and [RocksDB](rocksdb.md) describe the two adapters.
